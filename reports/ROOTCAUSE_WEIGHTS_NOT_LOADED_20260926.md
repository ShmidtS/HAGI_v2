# Корневая причина расхождения v1/v2 — родительский чекпойнт НЕ загружался

Дата: 2026-09-26. Найдено независимым аудитом, подтверждено исполнением.

## Симптом

Один и тот же сид 1234, один и тот же holdout (`row_ids_sha256`
побайтово совпадают), один и тот же transform digest — но `incumbent_macro_ce`:

- v1 (`recursive_growth_banking77_gen2_seed_1234`): 8.122496
- v2 (`recursive_growth_pp_seed_1234`): 8.101092

Разница 0.021404 ната.

## Причина

`build_model_from_payload` в `src/hagi/model/merge.py` конструировал модель
по конфигу и **не загружал в неё переданные веса**.

Коммит HEAD (`git show HEAD:src/hagi/model/merge.py`, строка 1683-1684):

    if cfg.merge.enabled:
        return MergedHAGI(cfg, ...).to(device)      # веса отброшены
    return HAGI(cfg).to(device)                      # веса отброшены

В рабочем дереве добавлено (`src/hagi/model/merge.py:1702`):

    model.load_state_dict(state, strict=True)

`_score_checkpoint_bytes` (`src/hagi/orchestrator/real_cycle.py:435,460`)
вызывает именно эту функцию. Значит **v1-семейство измеряло свежую
случайно инициализированную модель**, а не обученного родителя.

## Что отвергнуто (проверено, а не предположено)

- **Порядок RNG**: `build_deterministic_parent` (`real_cycle.py:281-303`)
  делает ровно один `torch.manual_seed(seed)` на `:290`, без
  branch-зависимого порядка. Трансформ-мод родителя не касается.
- **Режим трансформа**: `real_cycle.py:630` выставляет
  `target_cfg.merge.ternary_lift_mode` только для кандидата; путь
  родителя его не читает.
- **Сама схема v1→v2**: введена коммитом `d028f1d` ("derive
  mechanism_supported from the verdict"), который тронул только вывод
  флага, а не конструирование родителя.
- **Веса чекпойнтов**: `parent/step-0000000.pt` в обоих семействах
  **побайтово равны** (все 16 тензоров). Расходится только конфиг
  (`ternary_lift_mode: None -> f3_tree`, `config_sha256` 492301b0… vs
  712ddf4d…). То есть объект один — изменилось то, КАК он
  инстанцируется при скоринге.

## Доказательство, что гвард настоящий

`tests/test_checkpoint_weight_loading.py` — фальсификатор. Прогон:

    с load_state_dict:      4 passed
    без load_state_dict:     4 FAILED
    восстановлено:           4 passed

Гвард реально роняет регрессию, а не декоративен.

## Что это означает для истории проекта

Отчёт `.omc/attempts/FINDING_checkpoint_weights_not_loaded.md` фиксирует
тот же дефект ранее. Следствия:

1. **Все v1-измерения, взятые через `_score_checkpoint_bytes` без
   последующей загрузки весов, — шум.** В частности, paired SE 0.0251 и
   «9/9 одно-знаковых дельт» из AGENT_WORKLOG — невалидны.
2. Прежний baseline (rev. 1) был измерен на v1 и **недействителен** как
   точка отсчёта. Пин переписан на v2 (`reports/BASELINE_PINNED_20260925.md`,
   rev. 2).
3. Ранжирование «f3_tree против parent_preserving» по v1-числам
   некорректно.

## Что осталось непроверенным

- **Причина расхождения схем сама по себе не объяснена** — она оказалась
  побочным эффектом, а не причиной. Схему v2 стоит либо откатить, либо
  задокументировать как несовместимую форматную версию; сейчас она
  меняется при изменении смысла флагов, что опасно для сопоставимости.
- Коммит `src/hagi/model/merge.py:1702` **не закоммичен**. Пока он в
  рабочем дереве, любой свежий запуск из чистого клона воспроизведёт
  невалидные измерения. Это блокирующий пункт условия 5 раздела 3
  («все пути кода, влияющие на результат, закоммичены»).

## Следующий шаг

Закоммитить рабочее дерево (шаг 3 был незакоммиченным) — но только по
явному указанию владельца репозитория. До этого любые новые числа
помечены как «не воспроизводимы из чистого клона».
