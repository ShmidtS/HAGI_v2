# Round 42: B_noise/B* — первый замер (leaf, untrained-init)

## Что сделано

`scripts/b_noise.py`: McCandlish-оценка по двум батчам (B=8/32
строк × 1024 токенов, 6 шагов каждый, fp32-нормы всех параметров,
таблицы включены), тайминги fwd+bwd -> t0/c.

## Замер (dbridge_leaf_s1, fresh init, bf16)

- B=8:  ‖g‖²=1.15e-2, step 544 ms
- B=32: ‖g‖²=8.63e-3, step 2038 ms
- ‖G‖² = 7.68e-3 | tr Σ = 3.05e-2 | **B_noise = 4.0 строк (~4k токенов)**
- t0 = 46 ms | c = 62 ms/строку | **B* = √(B_n·t0/c) = 1.7 строк**

## Чтение (осторожное)

1. Конфиг 32 строки = 32k токенов/шаг — **~8× выше B_noise**:
   мы в deterministic-режиме; дальнейший рост батча заведомо
   бесполезен (подтверждает эпоху-1 вывод «batch 64 не помог»).
2. B* = 1.7 строк — НЕ руководство к действию напрямую:
   - замер на fresh init (B_noise растёт по мере обучения —
     McCandlish: у обученных моделей шум обычно больше);
   - t0/c измерены только по fwd+bwd; optimizer step + data
     pipeline смещают оптимум вверх;
   - формула T(B)=(1+B_n/B)(t0+cB) предполагает сходимость по
     токенам, реальный бюджет фиксирован по шагам (1600).
3. Слепой прогноз для A/B (если запускать): batch 8×1024 с
   4× числом шагов на том же токен-бюджете ≈ паритет или хуже
   по wall-clock (шаги не бесплатны), но кривая CE-per-step
   должна быть круче у малого батча до ~26k шагов.

## Дополнение: обученный чекпоинт (step-1600)

- B=8:  ‖g‖²=83.20 | B=32: ‖g‖²=82.70
- ‖G‖² = 82.5 | tr Σ = 5.4 | **B_noise = 0.1 строки (~100 токенов)**
- Обученный лист ПОЛНОСТЬЮ детерминирован: шума почти нет,
  B* → 0.2 строки. Батч — чистый throughput-инструмент.

Контринтуитивно vs McCandlish-картинки (у них S_n растёт при
обучении) — у нас loss-ландшафт листа после 52M токенов на
миксе 8 корпусов почти без стохастики на масштабе батча. Это
само по себе сигнал: следующий прирост качества — не из
батч-размера, а из механизмов (merge/rank/data).
