# Vocab-sliced leaves: измерено, отклонено

## Идея

Лист отвечает только за свой срез словаря (32768/9 ≈ 3641 токенов), вход
полный. Мотивация: убрать дублирование эмбеддинга — 96% весов листа.

## Реализация (рабочая, без хаков)

- `HAGI_VOCAB_SLICE="i:9"` в train.py → `trainer.slice_bounds` в loop.py:
  позиция скорится только если её TARGET в срезе. Вход — полный словарь,
  каждый лист видит весь контекст (это критично для concat-сборки).
- Первая попытка — маска через `log_prior` bias −1e4 — **провалилась
  честно**: CE 2357, потому что чужой таргет внутри softmax с bias −1e4
  даёт бесконечный loss. Правильно — маска в loss, не в логитах.
- 9 срезанных листьев обучены (s2001–s2009, 800 шагов, seed 2001–2009).

## Замер (один held-out, sweep logit_scale, swiglu, effective_sparse)

| модель | best CE |
|---|---|
| flat9 из ПОЛНЫХ листьев | **8.2837** |
| flat9 из СРЕЗАННЫХ листьев | 10.0679 |

**Срез проигрывает 1.78 ната.** Это не шум и не температура — методика
та же, что дала flat9 → 8.28.

## Почему (диагноз по механике)

Срезанный лист за 800 шагов видит в ~9 раз меньше скоримых позиций —
эффективный бюджет обучения упал в 9 раз при той же архитектуре. Его тело
учится «контекст → свой срез», но позиций太少: каждый лист получил ~1/9
обучающего сигнала. Проигрыш почти точно равен проигрышу листа, обученного
в 9 раз меньше, — то есть срез не сломан, он просто голодный.

Отдельный минус: специализация по ID токена, а не по смыслу. Токены среза
рассеяны по частям речи и темам — лист не получает связной задачи.

## Вывод

**Отклонено измерением.** Дешёвые срезанные листья = голодные листья.
Экономия весов не окупает потерю обучающего сигнала.

## Что осталось жить из этой идеи

- Эмбеддинг-инициализация уже нормальная по всему словарю
  (`embedding.py:64`, std=0.02) — эта часть идеи уже была реализована.
- Механизм `HAGI_VOCAB_SLICE` + loss-mask остаётся в коде как рабочий
  инструмент (годится для других экспериментов: доменные срезы, adaptive
  sampling частотных диапазонов).
- Если вернуться к идее — то со **срезом по данным, а не по ID**: лист
  специализируется на домене (ru/en/math/code), где срез связен. Это ровно
  Branch-Train-Merge, и это уже запланированная ветка.
