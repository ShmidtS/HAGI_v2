# GLM-5.3 как источник листьев: разбор (проверено запуском, 2026-09-26)

Источник: `\\wsl.localhost\Ubuntu-24.04\mnt\samsung\home\shmid\glm53`
(тот же путь, что и в вопросе пользователя). 306 ГБ, 62 шарда, 76108 тензоров.
Читается с Windows быстро: 1.2 ГБ эмбеддинга за 1.6 с через `safe_open`.

## Три препятствия, каждое измерено, а не прочитано

### 1. Модель гибридная: линейная ретракция чередуется с полной

`text_config.layer_types` — 45 слоёв, из них только 12 имеют
`deepseek_sparse_attention` (индексы 3, 7, 11, ...), остальные
`linear_attention` (KDA, gated delta net). Это РАЗНЫЕ архитектуры.

Слой 0 (linear_attention) — 16 проекций, ни одна не является обычным QKV:
```
self_attn.q_proj / k_proj / v_proj   [8192, 4096]   (MQA-подобно, без отдельных голов)
self_attn.q_conv1d / k_conv1d / v_conv1d [8192, 1, 4]  (свёртка k=4)
self_attn.f_a_proj / f_b_proj / g_a_proj / g_b_proj  (low-rank gate)
self_attn.A_log [64], dt_bias [8192]   (состояние линейной ретракции)
```

Слой 3 (deepseek_sparse_attention) — 20 проекций, и они другие:
```
self_attn.q_a_proj [1536,4096] -> q_b_proj [16384,1536]   (low-rank Q, ДВА шага)
self_attn.kv_a_proj_with_mqa [512,4096] -> kv_b_proj [32768,512]
self_attn.indexer.*  (6 тензоров)       (специфичный sparse-индекс)
self_attn.o_proj [4096,16384]
```

У HAGI-листа один путь: fused `qkv_proj (640, 384)` = 6q+2k+2v. **Ни один
слой GLM-5.3 не сводится к нему напрямую.** Пришлось бы изобретать
преобразование, для которого нет прецедента, а результат всё равно
пришлось бы дообучать — то есть мы заплатили бы 306 ГБ чтения и кусок
нового кода за инициализацию, которую всё равно переучим.

### 2. Веса квантованы в FP8, и обратно деквантовать их — отдельная задача

Заметная часть весов — `F8_E4M3` с парным `weight_scale_inv`:
```
self_attn.q_a_proj.weight          F8_E4M3  [1536, 4096]
self_attn.q_a_proj.weight_scale_inv F32    [12, 32]     # поблочный масштаб
self_attn.o_proj.weight            F8_E4M3  [4096, 16384]
self_attn.o_proj.weight_scale_inv  F32     [32, 128]
mlp.shared_experts.gate_proj       F8_E4M3  [2048, 4096]
```
Форма `weight_scale_inv` — двумерная (число блоков по каждой оси), то есть
поблочное масштабирование, а не один скаляр на тензор. Деквантование
`(W_fp8 * scale)` — это ручная операция над fp8-типами, для которой в
проекте нет ни кода, ни проверенной реализации.

### 3. MoMENTS: 288 routed + 1 shared эксперт на слой

```
mlp.experts.E.{gate,up,down}_proj   12384 тензоров (43 слоя x 288)
mlp.shared_experts.{gate,up,down}   43 слоя x 3
mlp.gate.weight [288, 4096]  +  e_score_correction_bias [288]
```
Лист HAGI — это ПЛОТНЫЙ SwiGLU шириной 384. Какой из 288 экспертов взять
и почему — вопрос без ответа в проекте. Взять shared — значит взять
крошечную часть модели.

## Сравнение с Gemma-4-E2B, лежащей локально

`~/.cache/huggingface/hub/models--google--gemma-4-E2B-it` — 9.7 ГБ,
`hidden_size 1536`, 35 слоёв, 8 q / 1 kv головы, `head_dim 256`,
`vocab 262144`, `intermediate_size 6144`. Веса bf16 (не квантованы),
обычный трансформер без MoE и без линейной ретракции.

У Gemma нет НИ ОДНОЙ из трёх проблем выше. Разница в стоимости импорта
несопоставима.

## Что предлагаю

Пользователь выбрал «листья из чужих моделей». Это правильная идея, и я
не отговариваю от неё. Но источник стоит выбрать так, чтобы конвертер
переводил геометрию, а не изобретал её. По измеренному:

- **Gemma-4-E2B** — конвертер сводится к честным обрезкам и детерминированным
  проекциям. Единственная содержательная часть — QKV 8q/1kv x 256 -> 6q/2kv x 64.
- **GLM-5.3** — конвертер обязан изобрести отображение гибридной
  KDA/sparse-ретракции на полный QKV и деквантовать FP8. Это не «конвертер»,
  это новый слой кода с нуля, без прецедента, без теста качества.

Рекомендую: сделать конвертер на Gemma-4-E2B как рабочий путь, а GLM-5.3
оставить как отдельную задачу «после». Если пользователь хочет именно GLM —
это честный выбор, но тогда это отдельный проект, а не шаг лестницы.

## Чего я НЕ сделал и почему

Не писал конвертер под GLM-5.3 до решения пользователя: сверху висит
делегация deep-специалисту с задачей под Gemma. Два конвертера сразу
расплодились бы, а переделка обошлась бы дороже. Сначала решение
источника, потом код.
