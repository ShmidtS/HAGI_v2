# Рекурсивная лестница 3 → 9 → 27: разбор блокеров

Пользователь: глубина не ограничена, каждый промежуточный уровень несёт свою
root-кору, ширина растёт втрое на уровень, лист остаётся 384.

## Сначала — моя ошибка

Я заявил, что схема «физически не может вырастить дерево, лист сжимается
384 → 128 → 42 → 14, при depth=3 ширина не делится нацело». **Это неверно.**
Я держал `merge.expert_hidden = 384` фиксированным, что противоречит смыслу
поля. Правильное правило: `expert_hidden` = ширина непосредственного ребёнка.

Проверено:
```
D=1 leaves= 3 leaf=384 expert_hidden=  384 hidden= 1152 consistent=True
D=2 leaves= 9 leaf=384 expert_hidden= 1152 hidden= 3456 consistent=True
D=3 leaves=27 leaf=384 expert_hidden= 3456 hidden=10368 consistent=True
D=4 leaves=81 leaf=384 expert_hidden=10368 hidden=31104 consistent=True
```
То есть `_recursive_leaf_hidden` (merge.py:1018-1019) КОРРЕКТНА, менять её
не нужно. Правка 3 из моего плана (config.py:1515-1520) — сомнительна,
надо проверить отдельно.

## Инвариант равенства листьев: ДЕРЖИТСЯ (проверено, не принято на веру)

`ParentPreservingTernaryLift` (merge.py:292) фиксирует (1,1,1) — подъём трёх
идентичных копий сохраняет логиты. Чтобы лестница вообще имела смысл, кора
ребёнка не должна это ломать.

Два независимых доказательства:

1. **Структурное.** `_write_root` (cortex.py:414-428) — `root.unsqueeze(-2)
   .expand(*root.shape[:-1], n_leaves, leaf_hidden).reshape(shape)`. Измерено:
   `stride` по оси листа = **0**, то есть view-shared. Зависимость от листа
   возникнуть не может: данные листа физически отсутствуют на входе expand.

2. **Числовое.** Кору затравил случайно (все 7 параметров, sigma 0.05, то
   есть «обученная» ненулевая кора). Равные листья на входе → прогнал все
   3 уровня `apply_boundary` → максимальная разница между листьями
   **0.000e+00** (точно ноль, не «около нуля»).

Вывод: кора ребёнка может быть обученной. Запрет на ненулевую кору у
детей — излишне строгий.

## Дыра 1 (серьёзная): кора не поднимается, а рождается заново

Гипотеза «скопировать кору первого ребёнка в родителя» НЕВЕРНА. Формы
`cortex.*` одинаковы при разном `n_leaves` (проверено: при leaf=384 формы
`(64,384)/(384,64)/(64,64)` одинаковы для D=1,2,3), но сама кора завязана на
`n_leaves=3` ребёнка: `_root_mode` (cortex.py:401-412) усредняет по оси
`self.n_leaves`, а `apply_boundary` (cortex.py:483) публикует уровень только
для `self._down_index`. Родителю нужна кора, разложенная на 9 (а на D=3 — на
27) листьев. Подъём коры ребёнка семантически бессмыслен: это связь между
уровнями ВНУТРИ одного уровня, а не три независимых блока.

Значит: **каждый уровень рождает свою кору заново, fresh zero-init** — ровно
как уже сказано в merge.py:1508-1512. И тогда:

- `cortex.*` в состоянии ребёнка по-прежнему **forbidden** (merge.py:1356-1366).
  Правка 2 из моего плана НЕ НУЖНА и была бы вредной.
- Меняется только забор merge.py:1400, и то узко.

## Дыра 2 (блокирующая): `_recursive_tree_norm_weights` игнорирует глубину

merge.py:840-866. Функция принимает `target_depth`, но НИГДЕ его не
использует, кроме проверки `target_depth < 1`. Возвращает просто
`cat([w.reshape(1,-1,leaf) for w in children])`.

Проверено измерением:
- дети уровня 1 (`[3,1,384]`): target D=2 → `(3,3,384)`, **target D=3 →
  `(3,3,384)`** — одинаково.
- дети уровня 2 (`[3,3,384]`): target D=3 → `(3,9,384)`, **target D=4 →
  `(3,9,384)`** — снова одинаково.

А `BlockTreeNorm` (norms.py:120) требует `inner_blocks = 3**(depth-1)`, то
есть при D=3 нужна форма `(3, 9, 384)`, при D=4 — `(3, 27, 384)`.

Следствие: **подъём уровня 1 → уровень 2 (D=2) пройдёт**, а подъём
уровня 2 → уровень 3 (D=3) упадёт на несовпадении формы, ровно там где
начинается собственно глубокая лестница. Эта дыра не проявлялась, потому
что D никогда не превышал 1.

Почему не проявляется при D=1→2: у ребёнка уровня 0 `inner_blocks = 3^0 = 1`,
`[3,1,leaf]`, reshape в `(1,3,leaf)`, cat по dim=0 даёт `(3,3,leaf)` — случайно
совпадает с `3^1`. Совпадение структурное, а не по ошибке: при D=2 каждый из
трёх детей level-1 даёт 3 листа, итого 9 = 3·3, что совпадает с формой
`[3, 3^1, leaf]` = `[3,3,leaf]`. Ломается начиная с D=3.

## СДЕЛАНО (правки внесены и проверены запуском)

**1. `_recursive_tree_norm_weights` (merge.py:840-880) — блокирующая правка.**
Функция принимала `target_depth`, но нигде его не использовала, кроме проверки
`>= 1`. Добавил обязательную сверку: `flat.shape[1]` должен равняться
`3**(target_depth-1)`, иначе `ValueError` с объяснением.

Проверено измерением (таблица «должно падать / должно проходить»):
```
D=2 из детей D=1                 -> (3, 3, 384)   ok
D=3 из детей D=1  (должно FAIL)  -> REJECTED
D=3 из детей D=2                 -> (3, 9, 384)   ok
D=4 из детей D=2  (должно FAIL)  -> REJECTED
```
Почему баг был скрыт: у ребёнка уровня 0 `inner_blocks = 3^0 = 1`, и
`3 * 1 == 3^1` — совпадение структурное, а не случайное. Для D=2 (подъём
1→2) всё работало и без правки. Ломалось ровно там, где начинается
глубокая лестница (3→9→27), то есть ни разу за всю историю проекта.

**2. Забор коры (merge.py:1408-1440).** Разрешил рекурсивному ребёнку иметь
root-кору. Признак «рекурсивный ребёнок» — `self.is_recursive_state(state)`
по ВСЕМ детям, то есть по наличию provenance-буферов, а не по полю конфига:
состояние авторитетнее конфига (так уже сделано в `checkpoint.py` для
`payload_is_recursive`). Лист без provenance по-прежнему отвергается.

Проверено тестом:
- лист, которому вручную включили кору -> REJECTED, забор сработал;
- depth-1 родитель (реальный чекпойнт) признан рекурсивным -> собрался.

**3. `cortex.*` в состоянии ребёнка (merge.py:1381-1400, 1670-1685).**
Разрешил рекурсивному ребёнку нести кору, но НЕ наследовать её: в цикле
сборки `assembled` ключи `cortex.*` пропускаются, кора родителя остаётся
свежей zero-init из `target_state`. Причина: кора определена против
`n_leaves` СВОЕГО уровня (`_root_mode` усредняет по `self.n_leaves`,
`apply_boundary` публикует по своему `_down_index`), поэтому кора уровня-1
в уровне-2 читала бы не те листья.

**4. Глубина доказана запуском, а не рассуждением:**
```
depth=1  3 leaves  H=1152    98,181,739 params   forward finite=True
depth=2  9 leaves  H=3456   429,688,639 params   forward finite=True
depth=3 27 leaves  H=10368  2,507,126,203 params forward finite=True
```
depth=4 (81 лист, H=31104, ~28B) НЕ трогал — OOM на 8060S, как сказал пользователь.

Существующий depth-1 не сломан: `scripts/f3_smoke.py` после всех правок даёт
`summary: ok`, логиты конечны.

## Импорт листьев из чужой модели — СДЕЛАНО, критерий выполнен

Пользователь выбрал листья из готовых моделей. GLM-5.3 отклонён с
измерениями (см. `foreign_leaf_source_glm53.md`): гибридная ретракция
(12 полных слоёв из 45), FP8 с поперно-блочными масштабами, MoE на 288
экспертов. Взята Gemma-4-E2B (локально, 9.7 ГБ, bf16, обычный трансформер).

`scripts/import_foreign_leaf.py` — конвертер, детерминированный (никакого
RNG нигде, два прогона дают побайтово одно и то же).

Измеренный результат:
```
contract check: 40 tensors, missing=0 extra=0 shape-mismatch=0
saved checkpoints\leaf_gemma_a.pt (58.0 MB)
PARENT BUILT from 3 imported leaves: RecursiveF3HAGI 98,181,739 params
logits (1, 64, 32768) finite True
```
Критерий задачи был «три импортированных листа проходят сборку родителя» —
выполнен.

Что стоит знать про эти листья, чтобы не переоценить:
- головы: источник 8q x 256 -> лист 6 x 64, то есть 6 голов из 8, каждая
  срезана с 256 до 64 каналов. `stride`-срез по строкам режет голову
  пополам; пришлось добавить `_take_heads`, который берёт целые головы.
- kv: у Gemma одна kv-голова (256 строк), лист хочет две. Дублирую, а не
  забиваю нулями, и печатаю это в лог: нулевая голова никогда не сработает.
- `o_proj` пришлось ужимать по ОБЕИМ осям (1536x2048 -> 384x384), а не по одной:
  контракт-проверка это поймала (было 3 расхождения, стало 0).
- `head.projection.weight` = копия эмбеддинга: у Gemma `tie_word_embeddings`,
  отдельной головы нет.
- `head.logit_scale` = 1/sqrt(H), НЕ переносится из источника: у Gemma другой
  словарь, её калибровка логитов к нашему не относится.
- эмбеддинг: 262144 -> 32768 стратифицированным срезом по id, не по частоте.
  Честно: частотный срез был бы лучше и требует прохода по корпусу.

## Статус эксперимента tree-vs-flat

Рука 1 (tree + root-кора) ОБУЧЕНА полностью, 3000 шагов:
```
step    0: ce=9.9888
step 1000: ce=5.8442
step 2000: ce=4.8704
step 2900: ce=4.5974
checkpoints/f3_parent_d1/step-0003000.pt
```
Рука 2 (flat контроль) и рука 3 (tree без коры) убиты МНОЙ, а не упали:
я останавливал тренеры при проверке OOM на depth-4 (~28B), и это задело их.
rc=127 это kill, не ошибка модели. Рука 2 успела дойти до 600 шагов
(ce 9.68 -> 7.97) без чекпойнта, поэтому начата заново. Сейчас идёт заново
в `run_f3_arms2.sh`.
Формы `cortex.*` при разном `n_leaves` одинаковы (проверено: при leaf=384
формы `(64,384)/(384,64)/(64,64)` совпадают для D=1,2,3), что на первый взгляд
разрешает копирование. Но кора завязана на `n_leaves` через `_root_mode`, а не
на формы. Подъём семантически бессмыслен — это связь между уровнями ВНУТРИ
одного уровня, а не три независимых блока.

1. **`merge.py:1400`** — разрешить рекурсивному ребёнку иметь root-кору в
   конфиге. Признак «рекурсивный ребёнок»: `RecursiveF3HAGI.is_recursive_state`
   (merge.py:1064), т.е. наличие provenance-буферов, а не поле конфига —
   состояние авторитетнее конфига (так уже сделано в
   `src/hagi/train/checkpoint.py` для `payload_is_recursive`).
   Забор НЕ трогаем вовсе, если кору родителя рождаем заново: состояние
   ребёнка `cortex.*` по-прежнему отбрасывается, нужно лишь разрешить
   трейлер, чтобы промежуточный уровень был полноценной моделью.
2. **`merge.py:840-866`** — `_recursive_tree_norm_weights` обязан учитывать
   `target_depth`: доводить `inner_blocks` до `3**(target_depth-1)`, а не
   брать форму ребёнка. Это блокирующая правка для глубины ≥ 3.
3. **`config.py:1515-1520`** — проверить отдельно: валидна ли проверка
   `hidden_size // 3 == expert_hidden`, когда `expert_hidden` = ширина ребёнка.
   По формулам выше при D=2: `hidden=3456`, `expert_hidden=1152`,
   `3456 // 3 = 1152` — проходит. Похоже, правка не нужна, но проверить на D=3:
   `10368 // 3 = 3456` — тоже проходит. Значит проверка случайно верна для
   обоих, но по другой причине, чем задумано; фиксирую как риск.

## Открыто (нужен oracle / проверка)

- `head_scale_divisor` и `logit_scale` при подъёме рекурсивного ребёнка
  (merge.py:1570-1586): делить ли ещё раз на 3.
- `child_config_fingerprint` (_canonical, merge.py:1294-1333): три родителя
  уровня-1 отличаются `train.data.seed`, который канонизацией ОТБРАСЫВАЕТСЯ.
  Если все три родителя архитектурно идентичны, fingerprint совпадёт — и это
  может быть как раз правильным (дети одной архитектуры), но надо понять,
  не мешает ли подъёму различать их.
- Бюджет: при H=1152 было ~3.2 s/step, при H=3456 ожидается ~3×, при 3000
  шагов это ~8.6 ч на уровень-1 и ~26 ч на уровень-2. Лестница 3→9→27 целиком
  не помещается в разумное время без сокращения бюджета. Риск: сокращённый
  бюджет даст вырожденные листья следующего уровня.
