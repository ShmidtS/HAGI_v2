# HAGI Architecture V2 — дерево с корой

Статус: проект решения. Ни один код здесь ещё не запущен.

## Проблема, которую это решает

Исходная гипотеза HAGI — рост **в глубину** тернарного дерева, а не в его
ширину. Измерено только обратное: плоское слияние одного уровня работает
(`docs/MEASURED_BEFORE_RESET.md`), а `merge_recursive_f3` /
`RecursiveF3HAGI` не запускались ни разу.

Второй механизм проекта — `PyramidalCortex`, направленные низкоранговые связи
между уровнями скрытых состояний. Код запрещает их совмещать:

| место | запрет |
|-------|--------|
| `config.py:1356` | `ternary_f3 requires cortex and decision disabled` |
| `merge.py:1354` | ребёнок не может нести `cortex.*` в состоянии |
| `merge.py:1392` | `child_m.cortex.enabled` отвергается |

## Забор — не осторожность, а инвариант

Коммит `2cc0e7c` поставил запрет без объяснения причины. Причина
существует, и она настоящая:

Тело F3 разлагает **всё** состояние по листьям.

- `BlockTreeNorm` (`norms.py:99`) нормует каждую лист-ветвь независимо;
  её вес имеет форму `[3, inner_blocks, leaf_hidden]`. Доксорт:
  «sibling leaves have different statistics», широкий RMSNorm по
  конкатенированному потоку не эквивалентен.
- `RecursiveBranchScale` (`ffn.py:26`) умножает каждую лист-подобласть на
  собственный скаляр и требует `hidden % n_leaves == 0`.
- `ParentPreservingTernaryLift` — ортогональное отображение, фиксирующее
  направление `(1,1,1)`. Три идентичные копии родителя при подъёме дают
  те же логиты: это и делает глубину осмысленной, а не деградирующей.

`PyramidalCortex.apply_boundary` добавляет к `h` слагаемое полной ширины.
Оно **не разложено по листьям**. Попав в следующее дерево, оно пройдёт
через `BlockTreeNorm`, которое исказит его по каждой ветви отдельно, и
через `RecursiveBranchScale`, которое домножит разные ветви разными
коэффициентами. Инвариант «три идентичных ребёнка → сохранённые логиты»
нарушается на первом же шаге.

Поэтому «просто снять флаг валидации» — неправильно. Это сломало бы
единственное свойство, ради которого существует `parent_preserving`.

## Решение: кора ходит по root-моде

Ортогональный lift расщепляет ширину родителя на два вида направлений:

- **root-мода** — диагональ `(1,1,1)`, среднее по листьям. Это и есть
  сигнал родителя: он одинаков во всех ветвях, поэтому lift его не трогает.
- **листовые моды** — две оставшиеся ортогонали к диагонали. Это сигнал
  различий между детьми; он принадлежит данному уровню и выше не поднимается.

Кора должна читать и писать **только root-моду**:

```
z_l = R_l( root(h_l) )                       # публикация: только диагональ
h'_l = h_l + rho * U_l( sum_{k<l} P_{k,l} z_k )   # запись: разворачивается
                                               # на все листья одинаково
```

Запись одинакова во всех листьях, значит она лежит на диагонали. Разберём
точно, что с ней происходит, потому что от этого держит весь дизайн.

Порядок внутри блока (`attention.py:448`):

```
h_in -> attn_norm(BlockTreeNorm) -> attn -> branch_scale -> h_out = h_in + scale_i * branch(...)
```

`BlockTreeNorm` нормует **вход ветви**, а не сам остаточный поток. Поток
`h` накапливается аддитивно и целиком не нормуется. Отсюда два разных
эффекта:

1. Слагаемое коры **доезжает по остаточному потоку нетронутым** —
   аддитивный проход через границу блока есть тождество.
2. Исказиться может только **чтение** этого слагаемого следующей ветвью:
   `BlockTreeNorm` применяет к каждой лист-подобласти свою статистику.

Теперь инвариант. Три идентичных ребёнка после `parent_preserving`-подъёма
дают `h`, одинаковое во всех листьях (lift — тождество на диагонали).
Кора, пишущая одинаково во все листья, сохраняет равенство: листья
`v + c` равны, `BlockTreeNorm` даёт на них один и тот же результат, ветви
читают одинаково. Значит **на инициализации инвариант выполняется ровно**.

Единственная оставшаяся угроза — `RecursiveBranchScale`, чьи `scale_i`
обучаются и могут разъехаться. Но она висит на теле F3 **независимо от
коры**: асимметрия ветвей ломает равенство листьев и без всякого
межуровневого канала. Кора не вносит нового нарушения, она лишь
разделяет уже существующий дрейф.

Плотная (`dense`) кора ведёт себя иначе: она пишет в листья **разные**
значения, равенство нарушается на шаге 0, `BlockTreeNorm` нормует листья
по разной статистике, и искажение возникает сразу, до всякого обучения.
Именно это и блокировал `config.py:1356`. Запрет был верным для плотной
коры и слишком широким для root-моды.

Формально: кора действует в факторпространстве дерева по диагонали. Это
в точности та роль, которую кора играет в плоской модели — там ширина
родителя и есть вся ширина, и кора пишет целиком.

## Почему это правильно по существу, а не обход

Древесная аналогия, которую дал пользователь — «у дерева есть кора» —
читается буквально в этой схеме:

- листья уровня — отдельные модели, их различия живут в листовых модах;
- ствол — root-мода, единственный канал, который переживает подъём;
- кора — то, что течёт **вдоль ствола между уровнями**, минуя листья.

Кора не соединяет листья. Она соединяет стволы уровней. Именно поэтому
она даёт глубину, а не ещё одну ширину: плоское слияние уже позволяет
переносить информацию между любыми точками широкого потока, и в нём кора
избыточна. В дереве с ограниченной шириной листа она — единственный
способ передать что-то между уровнями, кроме того, что влезло в root-моду.

Это и есть проверяемое утверждение, которого не хватает проекту:
**при равных параметрах дерево с root-корой лучше плоского слияния.**
Плоское слияние при той же ширине имеет доступ ко всей информации всех
детей напрямую; дерево — только к их диагонали. Если кора не окупает
эту потерю, глубина не нужна вовсе.

## Что меняется в коде

| файл | изменение |
|------|-----------|
| `cortex.py` | `RootModeCortex`: `down`/`up` работают над `root(h)`, запись разворачивается на диагональ. Наследует `AdaptiveComponent`, ownership по маркеру сохраняется. |
| `config.py:1356` | запрет сменяется на: `ternary_f3` требует `cortex.mode == "root"`; `dense`-кора по-прежнему отвергается, с тем же обоснованием. |
| `merge.py:1354,1392` | `cortex.*` остаётся запрещённым в **детях** (это верно: кора родителя — fresh state, как и в плоском пути), но разрешается в **конфиге родителя**. |
| `merge.py` (`from_state_dict`) | `BlockTreeNorm`/`RecursiveBranchScale` уже ставятся; добавить построение `RootModeCortex` для родителя. |

Семантика слияния не меняется: `cortex.*` не наследуется от детей,
новый уровень получает fresh zero-init. Это уже так в плоском пути
(`merge.py:1821-1835`) и это правильно — рёбра `P_{k,l}` описывают
взаимодействие уровней, которых у ребёнка не было.

## Открытые вопросы до реализации

1. **Геометрия root-моды.** `root(h)` — среднее по `n_leaves` ветвям,
   ширина `leaf_hidden`. Значит `down`/`up` коры имеют ранг относительно
   `leaf_hidden`, а не полной ширины. При `depth=2` это 1/9 ширины
   родителя: пропускная способность ствола падает с глубиной. Надо
   измерить, достаточно ли `rank=64` на leaf-ширине 128.
2. **Дрейф `branch_scale`.** Равенство листьев держится ровно, пока
   `scale_i` совпадают. Проверить, что при обучении дерева с корой
   разброс `scale_i` не растёт быстрее, чем в дереве без коры, — иначе
   кора ускоряет распад инварианта, и тогда её надо крепить к
   симметризованному `branch_scale`.
3. **`num_levels` в дереве.** Кора делит `model.blocks` на уровни. В
   родителе блоки те же, что у ребёнка, — значит уровни определяются
   шириной листа, а не родителя. Проверить на `depth=1`, что
   `is_boundary` не разъезжается.
4. **Сколько уровней дерева нужно, чтобы кора окупила потерю ширины.**
   Это и есть эксперимент, а не предположение.

## Что это НЕ решает

Дерево остаётся непроверенным, пока не обучено. Настоящий документ —
проект механизма, а не результат. Числа будут только после прогона
дерево-против-плоское при равных параметрах.
