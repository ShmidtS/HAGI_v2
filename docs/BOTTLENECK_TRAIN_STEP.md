# Профиль тренировочного шага: что реально стоит время

Измерено 2026-09-26 на ROCm 7.13 / gfx1201, torch 2.10+rocm7.13,
`TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`.

## Главный факт

Модель 80.2M (H=1152, 3 слоя, vocab 32768), batch 8 × 1024 токена,
`precision=bf16`, `ternary_fp32_master=False`:

**полный шаг 515 ms → 1.94 шага/с, 0.02 M токенов/с**

## Метод: профилировать так же, как это делает train.py

Первая версия этого профиля дала чудовищные 5005 ms на шаг, и это была
ошибка измерения, а не узкое место модели. Модель была построена и
перенесена на GPU, но **без `cast_model`**, то есть осталась в fp32.
Реальный `train.py` вызывает:

```python
cast_model(model, cfg.train.precision, ternary_fp32_master=...)
```

который приводит модель к bf16, оставляя fp32 только у модулей с
`keep_fp32` (нормы, обучаемые скаляры) — сознательное решение, потому что
обновления норм около 1e-4 не переживают bf16-шаг ~0.0078 у единицы
(`src/hagi/model/norms.py:44`).

Проверено: `encoder` выдаёт bf16, полный шаг 515 ms.

## Распределение времени (при корректном bf16)

| замер | время |
|-------|-------|
| блок целиком fwd+bwd | 71.5 ms |
| блок fwd+bwd без градиентов по весам | 53.4 ms |
| attention fwd+bwd | 285.8 ms |
| mixer fwd+bwd | 872.1 ms |
| encoder fwd+bwd | 27.9 ms |
| SDPA `[8,18,1024,64]` fwd | 3.46 ms |
| SDPA fwd+bwd (is_causal) | 9.32 ms |
| **полный шаг** | **515 ms** |

Строки «attention 285.8 ms» и «mixer 872.1 ms» сняты на изолированном
модуле с `float().sum().backward()` и **не** складываются: это замеры
разных конфигураций вызова, а не вклад в реальный шаг. Для распределения
использованы хуки по модулям на реальном шаге.

Реальное распределение по forward-хукам (565 ms суммарно):

```
blocks.0      295.8 ms   (первый блок включает warmup lazy-инициализацию)
encoder         80.6 ms
blocks.1        67.9 ms
blocks.2        67.2 ms
encoder.conv    33.0 ms
encoder.norm    14.2 ms
encoder.emb      5.7 ms
out_norm         0.5 ms
```

Голова (`LMHead`) в хуках не видна: полный CE по 32768 считается
`_ChunkedCrossEntropy` вне `forward` модуля.

## Что проверено и отброшено

**BitLinear в fp32.** Один BitLinear 1152→3072: 62.6 ms в fp32 против
7.3 ms в bf16 (8.6×). Казалось бы, вот и узкое место. Но:

- после `cast_model` BitLinear-веса **уже bf16**, потому что
  `ternary_fp32_master` по умолчанию `False`;
- замер с явным `ternary_fp32_master=True` даёт те же ~518 ms.

Вывод: fp32-путь реален, но не используется по умолчанию. Правка
`BitLinear.__init__` на `master_dtype=bfloat16` была сделана, замерена и
**откачена**: 518 ms против 515 ms, то есть в пределах шума, при добавленном
риске. Не оставляю в коде то, что не доказуемо ускоряет.

**Ternary step-cache.** 8073 ms с кэшем против 8156 ms без — разницы
нет. Кэш не является узким местом в bf16-режиме.

**`float().sum()` против `.sum()` в цели обратного прохода** — 27 против
26 ms, шум.

## Вывод

Реальное узкое место — **сам размер matmul в полном vocab**: полный CE по
32768 при `sampled_softmax_k=0`. При `ce_chunk_rows=4096` и N=8192 это
два чанка, каждый с softmax на весь алфавит. Плюс `encoder.conv` на 33 ms
при 1152 ширины — заметная доля на слой.

Следующие кандидаты на замер, в порядке ожидаемого эффекта:

1. `sampled_softmax_k > 0` на тренировке вместо полного CE (измеряем
   потери точности против скорости на фиксированном held-out).
2. Увеличить `ce_chunk_rows` — снять накладные расходы нарезки.
3. `encoder.conv`: снять или удешевить — 33 ms из 565 это 6%.
4. `ce_keep_rate` < 1.0 — уже используется в прошлых прогонах (0.25).

## Связь с принципом Quail

Quail выигрывает не «быстрыми матрицами», а отказом считать лишнее.
Здесь та же картина: полный CE по 32768 — это ровно та работа, которую
`sampled_softmax_k` позволяет не делать на каждом шаге. Принцип тот же,
уровень другой: Quail переиспользует KV между предиктами, здесь
сэмплирование уменьшает алфавит до 2048 кандидатов.
